流式接口 vs 普通接口分析

以下是两个接口的详细对比分析：

核心区别分析

特性 普通接口 (generate) 流式接口 (generate_stream)
响应类型 ChatResponse (单个对象) Flux<ChatResponse> (响应流)
调用方法 chatClient.call() chatClient.stream()
通信模式 同步阻塞 异步非阻塞
数据传输 一次性完整返回 分块流式传输
延迟表现 高延迟（等待完整响应） 低延迟（首个token快速返回）
内存占用 高（需缓存完整响应） 低（分块处理）
适用场景 短文本、简单响应 长文本、实时交互
网络要求 较低（单次请求响应） 较高（保持长连接）
错误处理 全有或全无 可部分成功
客户端体验 等待期间无反馈 实时渐进式展示

    Server->>LLM: 发送完整请求
    Note over LLM: 处理完整请求<br/>生成完整响应

sequenceDiagram
    participant Client

    participant LLM
    
    Client->>Server: HTTP GET /generate_stream
    Server->>LLM: 启动流式请求

    LLM->>Server: 返回结束标志
    Server->>Client: 发送[结束]事件

技术实现差异

  1. 响应处理

  • 普通接口：

    • 等待大模型生成完整响应
    • 一次性序列化为JSON返回
    • 客户端需等待完整响应才能显示

  • 流式接口：

    • 使用Server-Sent Events(SSE)或HTTP流
    • 每个token/片段到达立即发送
    • 客户端可增量渲染内容
  1. 资源管理

  • 普通接口：

    • 占用线程直到完整响应生成
    • 高并发时易导致线程池耗尽

  • 流式接口：

    • 基于Reactive编程模型
    • 非阻塞I/O，资源利用率高
    • 适合处理大量并发请求
  1. 错误处理

  • 普通接口：

    • 任何错误导致整个请求失败
    • 客户端需完全重试

  • 流式接口：

    • 可发送错误事件而不终止流
    • 部分成功场景下仍可返回已生成内容
    • 支持更精细的错误恢复策略

其实本质上，这个普通接口和流式接口都是调用大模型接口并返回数据，但是后者可以间断性持续保持联系，然后获取到服务器上面返回的数据。

使用知识库

获取知识库的内容，然后构建上下文和大模型交互

以下是对代码的详细注释和功能分析：

  1. RAG（检索增强生成）流程：

    • 检索阶段：从向量数据库（pgVectorStore）检索与用户问题相关的文档
    • 生成阶段：将检索结果注入大模型提示词，指导生成过程

  2. 关键处理步骤：

    graph TD
A[用户输入消息] --> B[向量数据库检索]
C[ragTag知识库标识] --> B
B --> D[合并Top5文档内容]
D --> E[构建系统提示词]
A --> F[创建用户消息]
E & F --> G[组合完整对话上下文]
G --> H[流式调用大模型]
H --> I[返回SSE响应流]

  3. 核心组件说明：

    • 向量检索：pgVectorStore.similaritySearch()
      • 使用余弦相似度查找相关文档
      • withTopK(5)：控制成本与质量的平衡点
      • knowledge字段过滤：实现多知识库隔离
    • 提示词工程：
      • 系统提示词强制要求中文回复
      • {documents}占位符动态注入知识
      • “act as if you knew” 技巧提升回答自然度
    • 流式响应：Flux<ChatResponse>
      • 适用场景：长文本生成/实时交互
      • 优势：降低客户端等待时间

上面的这个 PgVectorStore 的包为 package org.springframework.ai.vectorstore;
