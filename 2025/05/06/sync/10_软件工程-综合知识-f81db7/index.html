10_软件工程-综合知识

1、软件工程概述

软件工程是一系列步骤和活动，用于创建和维护软件系统。它包括软件开发生命周期（SDLC）的各个阶段，以及相关的文档和工具。

软件开发生命周期（SDLC）

  1. 软件定义时期：
    • 包括可行性研究和详细需求分析。
    • 任务是确定软件开发工程必须完成的总目标。
    • 具体步骤包括问题定义、可行性研究、需求分析等。
  2. 软件开发时期：
    • 涉及软件的设计与实现。
    • 具体步骤包括概要设计、详细设计、编码、测试等。
  3. 软件运行和维护：
    • 将软件产品移交给用户使用，并进行持续的维护和更新。

软件系统文档

  • 用户文档：描述系统功能和使用方法，不涉及功能实现细节。
  • 系统文档：描述系统设计、实现和测试等详细内容。

软件工程过程

  1. P(Plan) - 软件规格说明：
    • 规定软件的功能及其运行时的限制。
  2. D(Do) - 软件开发：
    • 开发出满足规格说明的软件。
  3. C(Check) - 软件确认：
    • 确认开发的软件能够满足用户的需求。
  4. A(Action) - 软件演进：
    • 软件在运行过程中不断改进以满足客户新的需求。

软件系统工具

  • 软件开发工具：
    • 需求分析工具、设计工具、编码与排错工具、测试工具等。
  • 软件维护工具：
    • 版本控制工具、文档分析工具、开发信息库工具、逆向工程工具、再工程工具。
  • 软件管理和软件支持工具：
    • 项目管理工具、配置管理工具、软件评价工具、软件开发工具的评价和选择。

软件设计活动

  • 数据设计：定义数据结构和数据库模式。
  • 架构（体系结构）设计：确定系统的高层结构和组件。
  • 人机界面（接口）设计：设计用户界面和交互方式。
  • 过程设计：定义系统的业务逻辑和工作流程。

总结

软件工程是一个系统化的过程，涵盖了从定义、开发、运行到维护的各个阶段。它依赖于详细的文档和各种工具来支持软件开发、维护和管理活动。通过这些活动和工具，软件工程师能够创建出满足用户需求的高质量软件产品，并确保产品的持续改进和适应性。

4、逆向工程

逆向工程是软件工程中的一个术语，它指的是分析已有的程序，目的是在比源代码更高的抽象层次上建立程序的表示。这个过程通常是为了理解程序的结构和功能，以便进行维护、升级或重构。

逆向工程的目的

  • 理解程序：在没有文档或源代码的情况下，理解程序的功能和结构。
  • 恢复设计：重新创建程序的设计文档，这有助于未来的维护和开发。
  • 软件复用：提取程序组件以便在新的软件项目中使用。
  • 改进和优化：基于对现有程序的理解，进行改进和优化。

逆向工程的四个级别

  1. 实现级：
    • 抽象级别最低，完备性最高。
    • 包括程序的抽象语法树、符号表、过程的设计表示。
  2. 结构级：
    • 包括反映程序分量之间相互依赖关系的信息。
    • 例如调用图、结构图、程序和数据结构。
  3. 功能级：
    • 包括反映程序段功能及程序段之间关系的信息。
    • 例如数据和控制流模型。
  4. 领域级：
    • 抽象级别最高，完备性最低。
    • 包括反映程序分量或程序诸实体与应用领域概念之间对应关系的信息。
    • 例如E-R模型（实体-关系模型）。

逆向工程过程能够导出过程的设计模型(实现级)、程序和数据结构信息(结构级)、对象模型、数据和控制流模型(功能级)以及UML状态图和部署图(领域级)。

其中，结构级包括反映程序各部分之间相关依赖关系的信息；功能级包括反映程序段功能及程序段之间关系的信息。

与逆向工程相关的概念

  1. 重构：
    • 在同一抽象级别上转换系统描述形式。
    • 目的是提高代码的可读性和可维护性。
  2. 设计恢复：
    • 借助工具从已有程序中抽象出有关数据设计、总体结构设计和过程设计等方面的信息。
  3. 再工程：
    • 在逆向工程所获得信息的基础上，修改或重构已有的系统，产生系统的一个新版本。
    • 包括逆向工程、新需求的考虑过程和正向工程三个步骤。
  4. 正向工程：
    • 从现有系统中恢复设计信息，并使用该信息去改变或重构现有系统，以改善其整体质量。

逆向工程是一个复杂的过程，它要求工程师有深厚的技术知识和分析能力。通过逆向工程，可以更好地理解、维护和扩展已有的软件系统。

5、需求工程 🚩

软件需求

软件需求是描述用户对软件系统或软件组件期望的一系列条件或能力。这些需求涵盖了用户期望系统所具有的功能、行为、性能、设计约束等方面。软件需求是软件开发过程中的关键部分，因为它们直接关联到产品最终能否满足用户的实际需要。

软件需求的分类

  1. 业务需求：
    • 反映企业或客户对系统高层次的目标要求。
    • 通常由项目投资人、客户、市场营销部门或产品策划部门提出。
    • 用于确定项目视图和范围。
  2. 用户需求：
    • 描述用户的具体目标或用户要求系统必须能完成的任务。
    • 通过用户访谈、问卷调查等方式收集，描述用户使用系统的场景。
  3. 系统需求：
    • 从系统的角度详细说明软件的需求。
    • 包括功能需求、非功能需求和设计约束。

系统需求的细分

  1. 功能需求：
    • 也称为行为需求。
    • 规定开发人员必须在系统中实现的软件功能。
    • 用户利用这些功能来完成任务，满足业务需求。
  2. 非功能需求：
    • 指系统必须具备的属性或品质。
    • 细分为软件质量属性（如可维护性、可靠性、效率等）和其他非功能需求。
  3. 设计约束：
    • 也称为限制条件或补充规约。
    • 对系统的一些约束说明，如必须采用特定的技术、框架、数据库系统或操作系统等。

软件需求的管理和开发

  • 需求开发：涉及收集、分析和文档化需求的活动。需求开发过程包括识别需求、确定需求的优先级、验证需求的完整性和一致性。
  • 需求管理：涉及需求的跟踪、变更控制和维护。需求管理确保需求在整个项目周期内保持更新，并且所有利益相关者对需求有共同的理解。

软件需求文档（Software Requirements Document, SRD）是需求开发过程中的重要产出，它详细描述了软件需求，并作为开发、测试和维护的基础。良好的需求管理是确保项目成功的关键因素之一。

需求获取

需求获取是软件开发过程中关键的一步，其目的是确定和理解项目干系人的需求和约束。这个过程帮助项目团队收集用户的具体需求、业务需求以及任何设计和实施的约束条件。以下是常见的需求获取方法：

  1. 用户访谈：
    • 与有代表性的用户进行一对一至一对三的交流。
    • 可以是结构化的（有预设问题列表）或非结构化的（更自由的对话形式）。
  2. 问卷调查：
    • 当用户数量众多，无法进行逐一访谈时使用。
    • 可以覆盖大量用户以收集需求和意见。
  3. 采样：
    • 从目标用户群体中系统地选择有代表性的样本集。
    • 样本数量的计算公式为：样本数量=0.25×(可信度因子错误率)2样本数量=0.25×(错误率可信度因子​)2
  4. 情节串联板：
    • 使用一系列图片或场景，通过讲故事的方式来表达和收集需求。
  5. **联合需求计划(JAD)**：
    • 通过组织会议，将关键用户代表、系统分析师、开发团队代表聚集在一起讨论需求。
  6. 需求记录技术：
    • 包括任务卡片、场景说明、用户故事、Volere白卡等方法，用于记录和整理需求。

需求获取的目标

  • 理解用户的真实需求：需求获取的最终目标是理解用户需要什么，以及他们希望通过系统解决什么问题。
  • 确定功能和非功能需求：明确软件所必须实现的具体功能和性能、可靠性、安全性等非功能需求。
  • 揭示潜在的约束：了解可能影响项目实施的任何技术、时间、预算等约束。
  • 建立共识：确保所有干系人对需求有共同的理解。

需求获取的步骤

  1. 准备：确定需求获取的目标、计划和方法。
  2. 执行：通过上述方法收集需求信息。
  3. 分析：对收集到的信息进行整理和分析，提取关键需求。
  4. 记录：将需求以一定的格式（如用户故事、用例等）记录下来。
  5. 验证：与用户确认需求的准确性和完整性。
  6. 管理：跟踪需求的状态，处理需求变更。

需求获取是需求管理的第一步，对于确保项目成功和最终产品满足用户期望至关重要。

需求分析

需求分析是软件开发过程中的一个关键阶段，它的目的是将用户的需求和期望转化为清晰、准确、无歧义的用户需求。这些需求将作为系统设计和实现的基础。

需求分析需要确保获取的需求满足特定的特点，如无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性和必要性。

需求分析的任务
  1. 绘制系统上下文范围关系图：确定系统的功能和边界。
  2. 创建用户界面原型：设计用户界面的初步版本。
  3. 分析需求的可行性：评估需求的技术可行性和经济合理性。
  4. 确定需求的优先级：根据重要性和其他因素对需求排序。
  5. 为需求建立模型：使用图表或模型来描述需求。
  6. 创建数据字典：为系统中使用的数据元素创建一个详细的参考资源。
  7. 使用 QFD(质量功能部署)
结构化的需求分析

结构化需求分析是一种系统化的方法，它采用自顶向下、逐步分解的方法来分析系统。它主要关注数据流和数据处理。

结构化特点: 自顶向下、逐步分解、面向数据.

结构化分析方法 ✈️

结构化分析方法是一种面向数据流的需求分析方法，其基本思想是自顶向下逐层分解。

数据流图是进行结构化分析时所使用的模型，其基本成分包括数据流、加工、数据 存储和外部实体。在进行结构化设计时，通过对数据流图进行变换分析和事务分析可以导出程序结构图。

数据库设计可以分为4个主要阶段：

  • ①用户需求分析。数据库设计人员采用一定的辅助工具对应用对象的功能、性能、限制等要求所进行的科学分析。
  • ②概念设计。概念结构设计是对信息分析和定义，如视图模型化、视图分析和汇总。对应用对象精确地抽象、概括而形成的独立于计算机系统的企业信息模型。描述概念模型的较理想的工具是E-R图。
  • ③逻辑设计。将抽象的概念模型转化为与选用的DBMS产品所支持的数据模型相符合的逻辑模型，它是物理设计的基础。包括模式初始设计、子模式设计、应用程序设计、模式评价以及模式求精。
  • ④物理设计。逻辑模型在计算机中的具体实现方案。

UML是面向对象软件的标准化建模语言，其中状态图、活动图、顺序图和通信图可以用来对系统的动态行为进行建模。活动图展现了在系统内从一个活动到另一个活动的流程。活动图强调对象之间的控制流程。在活动图上可以表示分支和汇合。活动图与传统的程序流程图是不等价的。

4 + 1 视图模型 ✈️

4+1”视图模型从5个不同的视角来描述软件架构，每个视图只关心系统的一个侧面，5个视图结合在一起才能反映系统的软件结构的全部内容。这5个不同的视角包括逻辑视图、开发视图、进程视图、物理视图和场景。

  • (1) 逻辑视图。逻辑视图主要支持系统的功能需求，即系统提供给最终用户的服务。在逻辑视图中，系统分解成一系列的功能抽象，这些抽象主要来自问题领域。在00技术中，通过抽象、封装和继承，可以用对象模型来代表逻辑视图，用类图来描述逻辑视图。

  • (2) 开发视图。开发视图也称为模块视图，在UML中被称为实现视图，它主要侧重于软件模块的组织和管理。开发视图要考虑软件内部的需求。

  • (3) 进程视图。进程视图侧重于系统的运行特性，主要关注一些非功能性需求。进程视图强调并发性、分布性、系统集成性和容错能力，以及逻辑视图中的功能抽象如何适应进程结构等，它也定义了逻辑视图中的各个类的操作具体是在哪一个线程中被执行。进程视图可以描述成多层抽象，每个级别分别关注不同的方面。

  • (4) 物理视图。物理视图在UML中被称为部署视图，主要考虑如何把软件映射到硬件上，它通常要考虑到解决系统拓扑结构、系统安装和通信等问题。

  • (5) 场景。场景可以看作是那些重要系统活动的抽象，它使4个视图有机联系起来。场景对应UML中的用例视图。

三大模型
  1. 功能模型：使用数据流图(DFD)来表示系统的输入、输出和处理过程。
  2. 行为模型：使用状态转换图来表示系统的状态和引起状态转换的事件。
  3. 数据模型：使用E-R图(实体-关系图)来表示系统中的数据元素及其关系。

数据流图(DFD)

数据流图是一种图形化工具，用于显示信息流和数据从输入到输出的传输过程。

基本图形元素

  • 数据流：表示数据的流向。
  • 加工：描述输入数据流到输出数据流之间的变换。
  • 数据存储：存储数据的地方。
  • 外部实体：系统之外的实体，如用户或其他系统。

DFD中常见的错误：

  1. 黑洞：有输入但没有输出的加工。
  2. 奇迹：有输出但没有输入的加工。
  3. 灰洞：输入不足以产生输出的加工。
状态转换图

行为模型：使用状态转换图来表示系统的状态和引起状态转换的事件。

E-R 图

数据模型：使用E-R图(实体-关系图)来表示系统中的数据元素及其关系。

数据字典(DD)

数据字典是需求分析的组成部分，为DFD中的元素提供详细定义。

  • 数据流：系统中传输的数据。
  • 数据项：数据流中的基本数据单位。
  • 数据存储：存储数据的结构。
  • 基本加工：DFD中的加工逻辑，描述数据的变换。
需求分析的方法
  • 结构化语言：使用结构化的方式来描述加工逻辑。
  • 判定表：一种表格形式的工具，用于描述复杂的条件和动作。
  • 判定树：一种图形化工具，用于表示决策过程中的条件和可能的结果。

需求分析是确保项目成功的关键步骤，它帮助团队理解用户的真实需求，并为后续的设计和实现阶段奠定基础。

基于 UML 的需求分析

基于UML的需求分析过程大致可分为以下步骤：

  • ①利用用例及用例图表示需求。从业务需求描述出发获取执行者和场景；对场景进行汇总、分类、抽象，形成用例；确定执行者与用例、用例与用例图之间的关系，生成用例图。
  • ②利用包图和类图表示目标软件系统的总体框架结构。根据领域知识、业务需求描述和既往经验设计目标软件系统的顶层架构；从业务需求描述中提取“关键概念”，形成领域概念模型；从概念模型和用例出发，研究系统中主要的类之间的关系，生成类图。

需求定义

需求定义，通常体现为软件需求规格说明书（Software Requirements Specification, SRS），是软件开发过程中的一项关键活动。其目的是确保项目干系人和开发团队对系统要达成的目标有一个共同且清晰的理解，为整个开发工作奠定基础。

需求定义的目的

  • 确立系统的基本功能和性能要求。
  • 形成项目干系人之间共识的文档。
  • 作为设计、实现和测试的依据。
  • 作为项目进度和质量控制的标准。

需求定义方法

  1. 严格定义（预先定义）：
    • 基于假设所有需求都能够被预先定义。
    • 假设开发人员与用户之间能够进行准确而清晰的交流。
    • 采用图形或文字来完整描述最终系统。
  2. 原型方法：
    • 采用迭代的循环型开发方式。
    • 认识到并非所有需求都能在系统开发前被准确说明。
    • 通过原型来克服项目干系人之间交流上的困难。
    • 特点包括：
      • 需要实际的、可供用户参与的系统模型。
      • 需要合适的系统开发环境。
      • 鼓励反复迭代，直到需求确定。
      • 一旦需求确定，遵循严格的定义方法。

需求定义活动的产物是软件需求规格说明书（SRS），它是软件开发过程中最重要的文档之一，对任何规模和性质的项目都至关重要。SRS为项目的顺利进行提供了明确的方向和依据。

需求验证

需求验证，也称为需求确认，是软件工程中的一个关键过程，其主要目的是确保所收集和记录的需求准确无误，并与用户的实际期望相一致。这个过程对于预防项目风险、确保项目成功至关重要。

需求验证的目的

  • 确保需求的准确性和完整性。
  • 确认需求的一致性和可行性。
  • 提供需求文档的正式验收标准。
  • 确保所有干系人对需求有共同的理解。

需求验证的步骤：

  1. 需求评审：
    • 正式评审：通过正式会议，让项目干系人（如客户、用户、开发团队、测试团队等）一起评审需求文档。
    • 非正式评审：通过日常工作交流，获取用户对需求的反馈。
  2. 需求测试：
    • 设计测试用例来验证需求的可实现性和正确性。
    • 测试用例基于需求文档中的描述，旨在验证每个功能和非功能需求。

需求验证的结果

  • 如果需求验证通过，需求规格说明书(Software Analysis Specification, SAS)将被用户签字确认，成为验收标准的一部分。
  • 一旦需求被确认，需求规格说明书成为需求基线。
  • 需求基线是项目的一个稳定参考点，之后的任何更改都需要通过正式的需求变更流程进行。

需求验证是确保项目按照用户期望进行的重要步骤，有助于减少项目失败的风险，提高用户满意度

系统设计主要目的：为系统制定蓝图，在各种技术和实施方法中权衡利弊精心设计，合理地使用各种资源，最终勾画出新系统的详细设计方法。

系统设计方法：结构化设计方法，面向对象设计方法。

系统设计的主要内容：概要设计、详细设计。

  • 单入口，单出口；

7、测试基础知识

测试原则

系统测试是为了发现错误而执行程序的过程，成功的测试是发现了至今尚未发现的错误的测试。

测试原则：

  • 应尽早并不断的进行测试；
  • 测试工作应该避免由原开发软件的人或小组承担；
  • 在设计测试方案时，不仅要确定输入数据，而且要根据系统功能确定预期的输出结果；
  • 既包含有效、合理的测试用例，也包含不合理、失效的用例；
  • 检验程序是否做了该做的事，且是否做了不该做的事；
  • 严格按照测试计划进行；
  • 妥善保存测试计划和测试用例；
  • 测试用例可以重复使用或追加测试。

测试方法

软件测试方法可分为静态测试和动态测试。

静态测试：指被测试程序不在机器上运行，而采用人工检测和计算机辅助静态分析的手段对程序进行检测，包括对文档的静态测试和对代码的静态测试。

对文档的静态测试主要以检查单的形式进行，而对代码的静态测试，包括桌前检查、代码审查、代码走查的方式。使用这种方法能够有效地发现30%-70%的逻辑设计和编码错误。

动态测试：指在计算机上实际运行程序进行软件测试，一般采用白盒测试和黑盒测试方法。

黑盒测试法：功能性测试，不了解软件代码结构，根据功能设计用例，测试软件功能。

白盒测试法：结构性测试，明确代码流程，根据代码逻辑设计用例，进行用例覆盖。

测试阶段

(1)单元测试：也称为模块测试，测试的对象是可独立编译或汇编的程序模块、软件构件或 00 软件中的类（统称为模块)
,测试依据是软件详细设计说明书。

(2)集成测试：目的是检查模块之间，以及模块和已集成的软件之间的接口关系，并验证已集成的软件是否符合设计要求。测试依据是软件概要设计文档。

(3)确认测试：主要用于验证软件的功能、性能和其他特性是否与用户需求一致。

根据用户的参与程度，通常包括以下类型：

  • 内部确认测试：主要由软件开发组织内部按照SRS进行测试。
  • Alphai测试：用户在开发环境下进行测试。
  • Beta测试：用户在实际使用环境下进行测试，通过改测试后，产品才能交付用户。
  • 验收测试：针对SRS,在交付前以用户为主进行的测试。其测试对象为完整的、集成的计算机系统。验收测试的目的是，在真实的用户工作环境下，检验软件系统是否满足开发技术合同或SRS。验收测试的结论是用户确定是否接收该软件的主要依据。除应满足一般测试的准入条件外，在进行验收测试之前，应确认被测软件系统已通过系统测试。

(4)系统测试：测试对象是完整的、集成的计算机系统；测试的目的是在真实系统工作环境下，验证完成的软件配置项能否和系统正确连接，并满足系统/子系统设计文档和软件开发合同规定的要求。测试依据是用户需求或开发合同。

主要内容包括功能测试、健壮性测试、性能测试、用户界面测试、安全性测试、安装与反安装测试等，其中，最重要的工作是进行功能测试与性能测试。功能测试主要采用黑盒测试方法；性能测试主要指标有响应时间、吞吐量、并发用户数和资源利用率等。

(5)配置项测试：测试对象是软件配置项，测试目的是检验软件配置项与SRS的一致性。测试的依据是SRS。在此之间，应确认被测软件配置项已通过单元测试和集成测试。

(6)回归测试：测试目的是测试软件变更之后，变更部分的正确性和对变更需求的符合性，以及软件原有的、正确的功能、性能和其他规定的要求的不损害性。

测试用例的设计

黑盒测试用例：将程序看做一个黑盒子，只知道输入输出，不知道内部代码，由此设计出测试用例，

分为下面几类：

  • 等价类划分：把所有的数据按照某种特性进行归类，而后在每类的数据里选取一个即可。等价类测试用例的设计原则：设计一个新的测试用例，使其尽可能多地覆盖尚未被覆盖的有效等价类，重复这一步，直到所有的有效等价类都被覆盖为止；设计一个新的测试用例，使其仅覆盖一个尚未被覆盖的无效等价类，重复这一步，直到所有的无效等价类都被覆盖为止。
  • 边界值划分：将每类的边界值作为测试用例，边界值一般为范围的两端值以及在此范围之外的与此范围间隔最小的两个值，如年龄范围为0-150，边界值为0,150,-1,151四个。
  • 错误推测：没有固定的方法，凭经验而言，来推测有可能产生问题的地方，作为测试用例进行测试。
  • 因果图：由一个结果来反推原因的方法，具体结果具体分析，没有固定方法。

白盒测试用例：知道程序的代码逻辑，按照程序的代码语句，来设计覆盖代码分支的测试用例，

覆盖级别从低至高分为下面几种：

  • (1)语句覆盖 SC:逻辑代码中的所有语句都要被执行一遍，覆盖层级最低，因为执行了所有的语句，不代表执行了所有的条件判断。
  • (2)判定覆盖DC:逻辑代码中的所有判断语句的条件的真假分支都要覆盖一次。

  • (3)条件覆盖CC: 针对每一个判断条件内的每一个独立条件都要执行一遍真和假。

  • (4)条件判定组合覆盖CDC:同时满足判定覆盖和条件覆盖。

  • (5)路径覆盖：逻辑代码中的所有可行路径都覆盖了，覆盖层级最高。

调试

  • 测试是发现错误，调试是找出错误的代码和原因。
  • 调试需要确定错误的准确位置；确定问题的原因并设法改正；改正后要进行回归测试。
  • 调试的方法有：蛮力法、回溯法（从出错的地方开始，向回找)、原因排除法（找出所有可能的原因，逐一进行排除，具体包括演绎法、归纳法、二分法)

软件度量. 🇺🇳

  • 软件的两种属性：外部属性指面向管理者和用户的属性，可直接测量，一般为性能指标。内部属性指软件产品本身的的属性，如可靠性等，只能间接测量。

  • McCabej度量法：又称为环路复杂度，假设有向图中有向边数为m,节点数为n, 则此有向图的环路复杂度为m-n+2.

注意m和n代表的含义不能混淆，可以用一个最简单的环路来做特殊值记忆此公式，另外，针对一个程序流程图，每一个分支边（连线）就是一条有向边，每一条语句（语句框)就是一个顶点。

8、系统运行与维护

系统转换

遗留系统是指任何基本上不能进行修改和演化以满足新的变化了的业务需求的信息系统，它通常具有以下特点：

  • (1)系统虽然完成企业中许多重要的业务管理工作，但仍然不能完全满足要求。一般实现业务处理电子化及部分企业管理功能，很少涉及经营决策。
  • (2)系统在性能上已经落后，采用的技术已经过时。例如，多采用主机/终端形式或小型机系统，软件使用汇编语言或第三代程序设计语言的早期版本开发，使用文件系统而不是数据库。
  • (3)通常是大型的软件系统，已经融入企业的业务运作和决策管理机制之中，维护工作十分困难。
  • (4)没有使用现代信息系统建设方法进行管理和开发，现在基本上已经没有文档，很难理解。

9、净室软件工程

净室软件工程（Cleanroom Software Engineering, CSE）是一种以数学和统计学为基础的软件工程技术，旨在以一种经济的方式生产高质量且几乎无缺陷的软件。这种方法强调从源头上预防缺陷的发生，而不是传统的先开发再测试和修复缺陷的方式。

净室软件工程的核心理念

  • 预防胜于修复：目标是在编码阶段第一次就正确地编写代码，避免后期昂贵的错误修正。
  • 统计质量控制：通过统计方法来控制和验证软件质量。
  • 零缺陷开发：力求在开发过程中达到零缺陷或接近零缺陷的状态。

净室软件工程的应用技术

  1. 统计过程控制：在增量开发过程中使用统计技术来监控和控制软件质量。
  2. 基于函数的规范与设计：使用数学函数来严格定义软件的行为和接口。
  3. 正确性验证：在编码之前验证软件规格和设计的正确性。
  4. 统计测试和软件认证：通过统计抽样和验证来测试软件，并进行软件认证。

净室软件工程的优点

  • 减少缺陷：通过预防性的开发过程减少软件中的缺陷。
  • 提高可靠性：生产更可靠、更稳定的软件产品。
  • 降低成本：减少后期修复缺陷的成本。

净室软件工程的缺点

  1. 理论化：需要较深的数学知识，对开发人员要求较高。
  2. 耗时：正确性验证步骤可能既困难又耗时。
  3. 不现实：不进行传统模块测试可能不现实，可能会遗漏一些实际运行中的问题。
  4. 传统弊端：尽管旨在避免缺陷，但仍可能带有传统软件工程的一些弊端。

总结

净室软件工程是一种以预防为主的软件工程方法，它通过数学和统计学方法来减少或消除软件缺陷。虽然这种方法可以提高软件质量，但它对开发人员的技能要求较高，且过程可能较为繁琐和耗时。因此，它可能不适用于所有类型的软件开发项目，特别是那些时间敏感或预算有限的项目。

10、基于构件的软件工程

基于构件的软件工程（Component-Based Software Engineering, CBSE）是一种软件开发方法，它侧重于通过识别、复用和组装现有的软件构件来构建新的软件系统。

这种方法体现了“购买而不是重新构造”的理念，并将软件开发的重点从编写新的代码转移到了基于已有构件的组装。

构件应具备的特征
  1. 可组装性：构件的所有外部交互必须通过公开定义的接口进行。
  2. 可部署性：构件必须是自包含的，能够作为独立实体运行。
  3. 文档化：构件必须完全文档化，以供用户判断是否满足需求。
  4. 独立性：构件应能独立于其他特殊构件进行组装和部署。
  5. 标准化：构件必须符合某种标准化的构件模型。

构件模型包含的要素

  1. 接口：构件通过定义好的接口与其他构件交互。
  2. 使用信息：构件需要有全局唯一的标识符或句柄。
  3. 部署：构件模型应包含如何将构件打包为独立可执行实体的说明。

构件模型提供的服务

  1. 平台服务：允许构件在分布式环境下通信和互操作。
  2. 支持服务：构件所需的共性服务，如身份认证服务。

中间件实现了构件所需的共性服务，并提供了这些服务的接口。

基于构件的软件开发过程（CBS过程）
  1. 系统需求概览：确定系统需求的高层次视图。
  2. 识别候选构件：寻找可复用的构件来满足需求。
  3. 根据发现的构件修改需求：根据可用构件调整需求以促进复用。
  4. 体系结构设计：设计系统的高层结构。
  5. 构件定制与适配：根据需要定制或适配构件。
  6. 组装构件创建系统：将构件组装成最终系统。

CBS过程与传统过程的不同点

  1. 早期需求的完整性：需要完整的早期需求以识别可复用的构件。
  2. 基于构件的需求细化：根据可用构件细化和修改需求。
  3. 体系结构设计后的构件搜索：在设计完成后进一步搜索和精化构件设计。
  4. 组装过程：开发过程主要是将找到的构件集成在一起。
  • 1、CBSE 早期需要完整的需求，以便尽可能多地识别出可复用的构件。
  • 2、在过程早期阶段根据可利用的构件来细化和修改需求。如果可利用的构件不能满足用户需求，就应该考虑由复用构件支持的相关需求。
  • 3、在系统体系结构设计完成后，会有一个进一步的对构件搜索及设计精化的活动。可能需要为某些构件寻找备用构件，或者修改构件以适合功能和架构的要求。
  • 4、开发就是将己经找到的构件集成在一起的组装过程。
构件组装方式

构件组装是指构件相互直接集成或是用专门编写的“胶水代码”将它们整合在一起来创造一个系统或另一个构件的过程。

常见的组装构件方式:

  1. 顺序组装：通过顺序调用构件。
  2. 层次组装：一个构件直接调用另一个构件的服务。
  3. 叠加组装：多个构件组合创建一个新构件，合并功能。

构件组装的不兼容问题

  1. 参数不兼容：操作的参数类型或个数不同。
  2. 操作不兼容：操作名称不同。
  3. 操作不完备：一个构件的接口是另一个构件接口的子集。

适配器：编写适配器来解决不兼容问题。

基于构件的软件工程强调复用和组装，可以提高软件开发的效率和质量。然而，它也要求有良好的构件管理和评估机制，以确保构件的适用性和兼容性。
